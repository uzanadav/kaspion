# Project Spec — Personal Finance Pipeline (codename: kaspion)

> **UPDATE (2026-07-03):** the dashboard decision changed after trying Evidence.dev in practice — it looked too "BI/business" and handled Hebrew/RTL poorly for family use. The dashboard is now a **self-contained interactive `dashboard.html` generated by `kaspion/report.py`** (pure HTML/CSS/vanilla JS, full RTL, no Node/server). Evidence references below are historical.

Handoff document for an AI coding agent (Claude Code / Cursor). Read this top to bottom before writing any code. Build in the phases defined below, in order.

## 1. Purpose & priorities (read this first)

**Primary purpose:** a household finance dashboard the owner AND his wife actually use. She is a non-technical user: her entire experience is opening a browser dashboard that is simple, in clear language, and answers "where did our money go and are we on budget?" at a glance.

**Secondary purpose:** a data/AI-engineering portfolio piece. The stack (dbt, DuckDB, MCP, semantic layer, LangGraph, evals) is the *bonus*, not the point. Whenever a design decision trades simplicity for tech showcase, **choose simplicity**. No feature ships if it makes the core dashboard harder to use or the pipeline harder to run.

**Cost constraint: everything must be free.** Every tool in this spec is free/open-source: Python, dbt-core, DuckDB, Evidence.dev, MCP SDK, LangGraph, Ollama, israeli-bank-scrapers, GitHub Actions (public repo). The ONLY potentially paid component is the Anthropic API for categorization — therefore **Ollama is the default provider** (fully free and offline). Claude API is an opt-in upgrade; with merchant memory, only *new* merchants are ever sent, so even opted-in it costs cents and trends to ~zero after the first month.

This is local-only and privacy-first: data never leaves the owner's machine.

## 2. The two build tracks

**Track A — the product (build first, Phases 0–5):** ingest → dbt models → AI categorization with merchant memory → Evidence dashboard → real bank scraper. Ends with: the family opens a dashboard showing their real spending. This is v1.

**Track B — portfolio bonus (Phases 6–9, any time after v1, any order):** eval harness, semantic layer + MCP server, LangGraph monthly-review agent, Docker + CI. Skippable or deferrable indefinitely without hurting the product.

## 3. Reference project (inspiration, NOT a template)

Inspired by "Spent" by Shaya16 (docs: https://shaya16.github.io/Spent/getting-started/ · repo: https://github.com/Shaya16/Spent). Borrow the idea and ethos:

- Local-only; Israeli bank/credit-card transactions.
- AI-assisted categorization with provider choice (local Ollama default, cloud Claude opt-in).
- "Merchant memory": corrections are remembered forever, AI never re-asked.
- Budgets with monthly pacing ("ahead/behind pace").
- Auto-detect transfers / credit-card payments; exclude from spend totals.
- Honest privacy posture (§10).

Do NOT borrow Spent's stack (Next.js/React/TypeScript/SQLite/Swift). We re-implement the concept on a data-engineering spine. The one reusable primitive is the Node library `israeli-bank-scrapers`.

## 4. Architecture

```
   Bank / credit card ──▶ israeli-bank-scrapers (Node)   (Phase 5)
                                    │  normalized JSON
   seed generator script ─┐        │
   (Phases 0–4 + tests)   ▼        ▼
                     Python ingest (writes raw.transactions)
                                    │
                                    ▼
                          DuckDB file (finance.duckdb)
                    ┌── raw schema (ingest writes)
                    ├── state schema (categorizer + overrides write; dbt READS ONLY)
                    │               │
                    │               ▼
                    └──▶ dbt (staging → transfer detection → marts → pacing)
                              with dbt tests at each layer
                                    │
              ┌─────────────────────┼──────────────────────┐
              ▼                     ▼                      ▼
   Evidence.dev dashboard   AI categorization       [Track B bonus:
   (THE product — simple,   + merchant memory        semantic layer + MCP,
    Hebrew-friendly pages)                            LangGraph agent, evals]

   Everything stays on the owner's machine (127.0.0.1 only).
```

**Key design rule #1 — the ingestion contract.** The contract between ingestion and everything downstream is the `raw.transactions` schema (§6.1). Phases 0–4 populate it from a seed generator; Phase 5's scraper writes the same schema. Nothing downstream changes.

**Key design rule #2 — state vs. dbt separation.** DuckDB holds three kinds of tables:

1. `raw.*` — written by ingest only.
2. `state.*` — mutable application state: `state.ai_proposals`, `state.merchant_overrides`, `state.budgets`. Written by the Python categorizer / CLI **only**. dbt declares these as **sources** and only reads them. dbt must NEVER materialize, rebuild, or truncate a `state.*` table — a `dbt build --full-refresh` must not touch them. Violating this silently wipes the owner's corrections.
3. dbt-managed models (staging/intermediate/marts) — rebuilt by dbt freely.

Do not add Airflow, Kafka, Spark, a cloud warehouse, or any paid/hosted service. Do not hand-write a React/Next.js frontend.

## 6. Data model

### 6.1 The ingestion contract: `raw.transactions`

Define this schema first — it is the stable contract.

| Column | Type | Notes |
|---|---|---|
| `transaction_id` | TEXT | Stable unique id. **Prefer the source-provided id when the bank supplies one (Phase 5).** Otherwise: `hash(posted_date, amount, raw_description, account_id, occurrence_idx)` where `occurrence_idx` is a `row_number()` over identical natural keys within the same day — prevents collisions on e.g. two identical coffees the same day. Used for dedup on re-ingestion. |
| `account_id` | TEXT | Which bank/card account. |
| `account_type` | TEXT | `bank` / `credit_card`. |
| `posted_date` | DATE | |
| `amount` | DECIMAL(18,2) | **Convention: negative = outflow, positive = inflow.** Document in README. israeli-bank-scrapers sources differ in sign convention — normalize at the scraper wrapper boundary, never downstream. |
| `currency` | TEXT | Default `ILS`. |
| `raw_description` | TEXT | Original merchant/description string (often Hebrew). |
| `source` | TEXT | `seed` during development, `<bank-name>` from the scraper. |
| `ingested_at` | TIMESTAMP | |

### 6.2 State tables (written by Python, read-only sources for dbt)

- `state.ai_proposals` — `transaction_id`, `proposed_category_id`, `provider`, `model`, `confidence`, `created_at`.
- `state.merchant_overrides` — normalized merchant key (§6.5) → `category_id`, `updated_at`. Upserted when the owner corrects a category.
- `state.budgets` — `category_id`, `monthly_amount_ils`, `effective_from`. Owner edits via a simple CLI command; wife only ever sees the result on the dashboard.

### 6.3 dbt layers

```
models/
├── staging/
│   └── stg_transactions.sql        -- clean/normalize, types, trim, normalized merchant key
├── intermediate/
│   ├── int_transfers_detected.sql  -- flag inter-account moves (§6.4a)
│   ├── int_card_payments.sql       -- flag monthly card-payment debits (§6.4b)
│   └── int_categorized.sql         -- AI proposals + merchant-memory overrides
│                                   -- (override ALWAYS wins)
└── marts/
    ├── fct_spend.sql               -- one row per real spend txn
    │                               -- (transfers AND card payments excluded)
    ├── dim_category.sql            -- simple category list, Hebrew display names
    └── fct_budget_pacing.sql       -- monthly target vs actual, day-of-month prorated
```

Categories: keep them few and household-friendly (~12–15, e.g. סופר, מסעדות, תחבורה, דיור, ילדים, בילויים…). A flat list with Hebrew display names beats a deep hierarchy nobody uses.

dbt tests (minimum):

- `unique` + `not_null` on `transaction_id` in staging.
- `accepted_values` on `account_type` and category fields.
- **Singular test: detected transfer pairs net to ~zero** (scope: §6.4a inter-account transfers only).
- **Singular test: card-payment exclusion** — no flagged card payment appears in `fct_spend`, and per closed billing month the bank-side debit ≈ that card's statement-period spend total (tolerance parameterized, e.g. ±1%).
- `not_null` on category in `int_categorized` output.
- `relationships` from `fct_spend.category_id` → `dim_category.category_id`.

### 6.4 Transfer & card-payment detection (SQL, not procedural code)

**(a) Inter-account transfers.** Pair = close in time (≤3 days), opposite sign, equal/near-equal absolute amount, across the owner's own accounts. Flag both; exclude from `fct_spend`. Net-to-zero test applies.

**(b) Credit-card payments — deliberately separate logic.** In Israel individual charges appear in the *card* account and one aggregate monthly debit (חיוב) appears in the *bank* account matching the statement total, NOT any single transaction. Not a pair-match: detect the bank-side debit by (bank account, counterparty matches known card-issuer patterns, amount ≈ that card's statement-period sum). Exclude the bank-side debit from `fct_spend` (card-side charges are the real spend). These get their own singular test, not the net-to-zero pair test.

### 6.5 Merchant memory

`state.merchant_overrides` keys on a **normalized merchant key** (staging: trimmed, casefolded, branch/store numbers stripped — "רמי לוי 342" → "רמי לוי") so one correction covers all branches. Resolution order in `int_categorized`: override → AI proposal → NULL (surfaced for review). Corrections always win; the AI is never re-asked about a known merchant.

## 7. Build plan — Track A: the product

Each phase must end runnable and tested. Do not start a phase before the previous "Done when" is met.

### Phase 0 — Repo skeleton

- Python project (`uv` + `pyproject.toml`), dbt-duckdb installed.
- dbt project initialized, `profiles.yml` → local `finance.duckdb`.
- README stub: architecture diagram + decisions section (all-free stack, DuckDB, no-Airflow, Ollama-default, state-vs-dbt rule, simplicity-first principle).
- **Done when:** `dbt debug` passes.

### Phase 1 — Seed generator + ingestion contract (NO scraper)

- Define `raw.transactions` (§6.1) and `state.*` tables (§6.2).
- `kaspion/ingest/generate_seed.py` — a **generator script**, not a static CSV. Parameterized (months, accounts, random seed). Output ~400–600 realistic rows: Israeli context, ILS, mixed Hebrew + English merchants, several months, ≥2 bank accounts + ≥2 cards, deliberate inter-account transfer pairs, and monthly card-payment debits summing to each card's statement period (so §6.4b has something real to catch). Writes `dbt/seeds/sample_transactions.csv`.
- `sync.py` seed mode: load into `raw.transactions` (dedup on `transaction_id`), then run dbt.
- **Done when:** `python sync.py` loads sample data and `dbt build` runs clean.

### Phase 2 — dbt modeling + tests

- Implement staging → intermediate → marts (§6.3) incl. both detection models (§6.4) and budget pacing.
- All tests from §6.3.
- **Done when:** `dbt build` passes incl. tests; `fct_spend` excludes the seeded transfer pairs and card-payment debits.

### Phase 3 — AI categorization + merchant memory

- Categorizer with a provider interface: `ollama` (DEFAULT — free, offline; e.g. a small local model), `claude` (Anthropic API, small model, opt-in), `none` (manual).
- Categorize uncategorized rows in batches; write to `state.ai_proposals`.
- `state.merchant_overrides` upsert via a simple CLI command (`kaspion recategorize "רמי לוי" groceries`) + override-wins join in `int_categorized`.
- While reviewing output on the seed, hand-label ~150–200 rows into `evals/ground_truth.csv` (labels double as QA now; the harness that consumes them is Track B).
- **Done when:** seeded transactions get categories; correcting a merchant and re-running keeps the correction without re-calling the model; `dbt build --full-refresh` does NOT lose overrides (add a check); `ground_truth.csv` exists.

### Phase 4 — Evidence.dev dashboard (THE product)

This is what the family sees. Design goal: **wife-proof** — she opens one URL and understands everything in 10 seconds, no training. Simple language (Hebrew labels), big numbers, no jargon, no filters she has to configure.

Evidence project in `dashboard/`, reading `finance.duckdb` (read-only). Pages:

1. **החודש (Home / this month):** one big number — spent so far vs. budget with a simple ahead/behind indicator ("אתם ₪420 מתחת לתקציב"), spend-by-category bar, biggest 5 expenses this month.
2. **קטגוריות (Categories):** per-category this-month vs. budget bars + 6-month trend per category on click.
3. **תנועות (Transactions):** searchable table (date, merchant, amount, category, which account). Also the review surface: rows where category came from AI (vs. override) are marked, so miscategorizations are easy to spot and the owner fixes them via the CLI.
4. **מגמות (Trends):** monthly total spend line, savings (income − spend) per month.

Requirements: Hebrew/RTL rendered correctly; sensible on a phone browser; binds to 127.0.0.1; no custom JS/CSS components — Evidence built-ins only (that's what keeps it simple AND good-looking).

- **Done when:** all four pages render against seed data, a non-technical user can answer "are we over budget this month and on what?" in under 10 seconds, and the pages are screenshot-ready for the README.

### Phase 5 — Real scraper (completes the product)

- Wrap `israeli-bank-scrapers` (Node) behind a clean interface outputting JSON matching the `raw.transactions` contract exactly — incl. sign normalization and preferring source-provided ids (§6.1). Start with ONE bank/card the owners actually use; add the others once stable.
- `sync.py --source scraper`: runs scraper → normalize → upsert into `raw.transactions` (dedup) → dbt → categorize new merchants. One command refreshes everything; optional cron/launchd for a daily run.
- Encrypt stored credentials at rest (AES-256-GCM, restricted-permission key file); never commit, never log. Follow §10.
- **Done when:** `python sync.py --source scraper` pulls real transactions and the dashboard shows the household's real finances. **This is v1 — the family can start using it.**

## 8. Build plan — Track B: portfolio bonus (after v1, any order)

### Phase 6 — Eval harness

- `evals/run_evals.py`: scores categorizer vs. `ground_truth.csv` — accuracy, per-category precision/recall, confusion summary; prints table, writes `evals/last_run.json`; supports comparing two providers (e.g. Ollama model vs. Claude Haiku — a genuinely useful comparison to publish).
- `EVALS.md` with methodology + numbers.

### Phase 7 — Semantic layer + MCP server

- Declarative YAML semantic layer: metrics (`total_spend`, `spend_by_category`, `budget_pace`) + dimensions (category, month, account, merchant) over the marts; small Python resolver compiling requests to SQL.
- MCP server exposing `query_spend`, `category_breakdown`, `budget_status`, `search_transactions` — resolved through the semantic layer, read-only, 127.0.0.1. Connectable from Claude Desktop/Code.
- Done when: "how much did we spend on restaurants last month vs. budget?" gets a grounded, correct answer in natural language.

### Phase 8 — LangGraph monthly-review agent

- Pulls the month via the semantic layer, flags overspend vs. budget and anomalies vs. prior months (simple robust stats, e.g. spend > k·MAD above trailing median), drafts a short Hebrew summary the owner can forward to his wife. On demand: `python -m kaspion.agent review --month 2026-06`.

### Phase 9 — Packaging + CI

- Docker Compose (pipeline + dashboard + MCP). GitHub Actions on push: ruff, `dbt build` against a freshly generated seed, evals with the `none`/fixture provider (no API key needed in CI, keeps CI free).

## 10. Privacy & security (non-negotiable)

- **Local-only.** Every server (Evidence, MCP) binds to `127.0.0.1` — never LAN/internet. Never deploy hosted. (If the wife's phone needs access, that's a future, deliberate decision — e.g. Tailscale — not a default.)
- `data/` gitignored; `finance.duckdb` backup-able by `cp`. Committed seed CSV is synthetic only — never real transactions.
- Credentials at rest: AES-256-GCM, restricted-permission key file, never committed, never logged.
- Outbound traffic allowed: the bank (scraper) and — only if `claude` provider is explicitly selected — the Anthropic API. Default (`ollama`) is fully offline.
- Bank scraping may violate ToS. Owners' own accounts, own machine only. Document in README/SECURITY.md.

## 11. Definition of done

**v1 (the product):** `python sync.py --source scraper` pulls the household's real transactions; dbt builds and passes all tests; transactions are categorized (Ollama default) with merchant memory that survives `--full-refresh`; the Evidence dashboard shows the family's real finances in simple Hebrew pages a non-technical user reads in seconds. All free, all local.

**v2 (the portfolio):** eval harness with published numbers, semantic layer + MCP natural-language querying, LangGraph monthly review, Docker + green CI.
